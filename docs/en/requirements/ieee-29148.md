# IEEE 29148 Requirements Fundamentals

The **ISO/IEC/IEEE 29148:2018** standard provides the engineering foundation for formulating unambiguous, verifiable, and traceable software requirements. This guide establishes the syntactic rules and evaluation criteria used by developers and AI agents.

---

## 1. The Standard Requirement Statement Syntax

According to IEEE 29148, individual requirement statements must follow strict syntactic templates to eliminate ambiguity:

```
[Condition / Trigger] + [Subject / System] + [Modal Verb] + [Action Verb] + [Object] + [Constraint]
```

### Modal Verb Rules (RFC 2119 / IEEE Standard):
- **SHALL**: Mandatory requirement; must be satisfied (Contractual invariant).
- **SHOULD**: Strongly recommended capability; can be omitted only with justified trade-offs.
- **MAY**: Truly optional or discretionary behavior.

---

## 2. Before vs. After: Applying IEEE 29148 Rules

### Example 1: Eliminating Ambiguity & Passivity
- ❌ **Bad (Vague & Passive)**: *"Student profiles should be updated quickly and safely."*
- ✅ **Good (IEEE 29148 Compliant)**: *"When a Student submits an updated phone number, the System **shall** validate the format against E.164 standard and persist the change within 200 milliseconds under a 500 concurrent-user load."*

### Example 2: Splitting Compound Requirements (Singularity)
- ❌ **Bad (Compound)**: *"The system shall allow users to search for internship jobs and export them as Excel and send an email alert."*
- ✅ **Good (Singular Statements)**:
  - *FR-01*: "The System **shall** allow an authenticated Student to filter active Internship Postings by technology tag."
  - *FR-02*: "The System **shall** export filtered Internship Postings to XLSX format within 2 seconds."
  - *FR-03*: "When a new Internship Posting matches a Student's saved filter, the System **shall** dispatch an email notification within 5 minutes."

---

## 3. Requirements Verification vs. Validation (V&V)

IEEE 29148 draws a crucial distinction between Verification and Validation:

```
┌─────────────────────────────────────────────────────────────┐
│                 VERIFICATION VS. VALIDATION                 │
├─────────────────────────────────────────────────────────────┤
│ • Verification: "Are we building the product RIGHT?"        │
│   (Checks conformance against specifications, rules, types) │
│                                                             │
│ • Validation: "Are we building the RIGHT product?"          │
│   (Checks whether software satisfies true user domain needs)│
└─────────────────────────────────────────────────────────────┘
```

## Input Requirement Text:
[INSERT RAW DRAFT REQUIREMENTS OR FEATURE NOTES]

1. Rewrite all input statements into IEEE 29148 compliant syntax using [Condition] + [Subject] + [SHALL/SHOULD/MAY] + [Action] + [Constraint].
2. Split all compound sentences into atomic, singular requirements.
3. Eliminate all vague adjectives (e.g. "fast", "scalable", "user-friendly") by specifying measurable verification criteria.

## 5. Review Checklist

- [ ] Does every requirement use normative modal verbs (`shall`, `should`, `may`) consistently?
- [ ] Is every statement atomic and singular (no "and also" compounding)?
- [ ] Is there an explicit verification method (Unit Test, Integration Test, Inspection) mapped to every requirement?
